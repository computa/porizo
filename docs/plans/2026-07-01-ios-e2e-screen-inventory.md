# Porizo iOS App — End-to-End Screen Inventory (Android Parity Reference)

**Purpose:** Canonical reference of every real, shipping SwiftUI screen in the Porizo iOS app, gathered for the Android port via Skip Fuse. The user's mandate is explicit: **"the android needs to be a replica of the ios"** — pixel and behavior fidelity, not reinterpretation. This document is the map; it does not contain implementation tasks.

**Scope note:** This catalog includes DEBUG-only design-comparison scaffolding (`CreationFlowRedesign/`, `V1Screens/`, `WarmCanvasScreenGallery`, `DesignSampleView`) because it was found during the audit, but these are explicitly flagged as **not for Android replication** — they exist only for internal design review on iOS and have no user-facing reachability in production.

**Revision note:** This document supersedes an earlier partial pass at the same path that covered 157 screens/components across 11 file groups. This revision is based on a complete parallel research pass across **15 file groups / 180 screens** plus a full completeness cross-check against the repo tree, and is the authoritative version going forward.

---

## 1. Summary

The catalog covers **180 distinct screens/components across 15 file groups**, of which roughly **120–130 are real production screens** reachable by an end user, and the remainder (~50) are DEBUG-only design-comparison scaffolding (`CreationFlowPickerView` + 6 option prototypes, `PostCreate` × 3, `V1ScreenCatalogView` + ~25 linked mocks, `WarmCanvasScreenGallery`, `DesignSampleView`, `LyricsOptionView` × 3) that must **not** be ported to Android as user-facing screens. The app's navigational skeleton is a single root state machine (`RootView`, enum `RootState`: `.splash → .onboardingV2 → .launchFlash → .auth → .main`) sitting above a **4-tab bottom bar** (`MainTabView`: Home/Explore, Songs, Poems, Settings — manually built, not native `TabView`, "to avoid black bar bug"). From `.main`, two full-screen-cover root flows dominate: **`WarmCanvasFlowView`** (the unified song/poem creation experience implementing "Four User Moments" — Tell → Wait → Reveal → Share) and **`GiftSendFlowView`** (gift reservation → composer → success, itself launching `WarmCanvasFlowView` for content creation). A third persistent surface, **`PlayerState`/`MiniPlayerBar`/`NowPlayingView`**, floats above all tabs once a track is loaded, entirely independent from the self-contained `TrackPlayerFullView` used immediately post-creation. Deep links (`porizo://`, `https://porizo.co/...`) route into `ShareClaimView`, `ReceiverClaimView`, and `PoemClaimView` for recipient-side flows.

**Highest-risk screens to replicate faithfully (in priority order):**

1. **`WarmCanvasFlowView`** — the single largest, most stateful screen in the app: owns ~10 controllers/coordinators, a `WarmCanvasMoment` state machine with nested sub-phases, resume-after-backgrounding recovery logic with a multi-branch version-state matrix, a 6-minute My-Voice-readiness poller with early-return branches, and gift-context handoff timing. A naive port will strand users in several resume/recovery paths.
2. **`AdaptiveConversationView` + `V2StoryEngine` conversation stack** (`ChatMessageBubble`, `InlineStoryCard`, `SuggestionChipsView`, `InputBarView`, `ElementGuidanceSheet`) — algorithmic inline-card placement, a hand-tuned local-guidance fallback generator (keyword matching against 5 per-beat templates), typewriter reveal timing, and a `canOfferUserFinish` heuristic combining 4+ independent signals.
3. **`PlayerState` vocal-onset lyric-sync system** (used by `NowPlayingView`) — client-side dB-power baseline + threshold + consecutive-frame detection at 30fps, with per-lyrics-style acceleration curves and lead-time offsets; has no direct Android/ExoPlayer equivalent and must be reimplemented, not simply ported.
4. **`GiftSendFlowView`** (3 sub-screens: content/composer/success) plus `GiftManagementSheet`/`ScheduledGiftListSheet` — a large multi-condition validation matrix (`canSave`, `canSendGift`) gating a StoreKit purchase-on-demand flow (`BundlePickerState`) that seamlessly resumes the original creation intent after purchase.
5. **Phone auth + account-linking state machine** (`PhoneAuthState` enum driving `PhoneAuthFlowView`) plus `AccountExistsView`'s cross-provider link flow — five states, country-specific phone formatting/validation asymmetry (+1 vs. everything else), and a "set pending link, cancel flow, wait for separate sign-in to complete" pattern that is easy to get only half-wired.

## 4. Non-Obvious Behaviors Android Must Replicate

Concrete, load-bearing edge cases pulled directly from `nonObviousBehavior` fields — a naive port will miss these.

**Auth & Account Linking**

- Apple Sign-In nonce uses rejection sampling (not modulo) against a 66-char alphanumeric+`-._` charset; empty-string return (not throw) on `SecRandomCopyBytes` failure.
- `ASAuthorizationError.canceled` is silently swallowed (no error banner) — every other Apple error code shows a specific message.
- Phone validation is asymmetric: +1 requires exactly 10 digits (or 11 with leading 1 stripped); all other countries require 6–15 digits after stripping one leading zero.
- Country auto-detection triggers on typed `+`, `00`, **or `011`** (US international dialing prefix) — not just `+`.
- Ambiguous +1 dial-code (US vs CA) always resolves to whichever appears first in the country list (US) since both have equal-length dial codes.
- AU phone formatting has a special two-pattern grouping (leading-0 vs not) baked into the formatter — a generic formatter will mis-group.
- OTP auto-submit races with manual tap — must guard with `!isVerifying` to prevent double-submission.
- A 429 status → distinct "too many requests" message; a 400 body containing "expired" resets the resend countdown to 0; a 400 body containing "invalid"/"incorrect" does not.
- `ProfileCompletionView.hasCompletedFirstSession` gates the skip button on account age >5 minutes (ISO8601 parse of `createdAt`) — **fails closed** (skip hidden) if unparseable, a deliberate anti-abuse choice.
- Google and Email sign-in buttons in `AccountExistsView` both wire to the identical handler — no separate Google OAuth path exists in this flow.

**Root Routing & Lifecycle**

- Scene-phase tracking explicitly ignores `.inactive` — only reacts to stable `.active`↔`.background` transitions via a shadow variable, because iOS delivers `.active→.inactive→.background` and a naive read misfires.
- Launch-flash has a circuit breaker: 3 consecutive resolve failures suppress it for the session; resets after 6 hours of staleness.
- `.appReturnedToForeground` is deliberately **not** posted on cold start — only on genuine backgrounded→foregrounded transitions (a documented past bug fix).
- Deep links support both host-based (`porizo://create`) and path-based (`https://porizo.co/create`) URL shapes for the same route, plus 3 legacy path-prefix aliases each for track vs. poem shares.
- Receiver deep-link claims skip onboarding entirely (`markOnboardingCompleted()` called directly) to get gift recipients to their song fast.
- Sheet presentation queuing pattern (seen in RootView, SettingsTabView, GiftSendFlowView) exists because presenting a new sheet mid-dismissal of another silently drops on iOS — always wait for `onDismiss` before firing the next presentation.

**Creation Flow**

- `WarmCanvasFlowView`'s resume logic has a matrix of ~6 version-states (full URL present / full job in-flight / preview URL present / preview job in-flight / failed-retriable / failed-no-job) each mapping to a different recovered UI moment.
- My-Voice readiness polling runs up to 36 attempts at 10s intervals (≥180s floor) even if the server hints a shorter estimate — an earlier under-estimate (30s) caused premature timeouts on the happy path.
- Enrollment recording validation is asymmetric: sung prompts require near-full-duration (`max(6, hinted-0.5)`s); spoken prompts only need 2s — stopping early on a sung prompt shows a specific "sing until timer finishes" error.
- `confirmStoryV2` (poem flow) can itself return `.needsInput` **before** poem creation starts, routing back to conversation rather than failing.
- `createPoemFromStory` can return `.gaps` instead of a poem, routing to an entirely different screen (`PoemGapQuestionView`), not an error state.
- Full-render approval requires an explicit `apiClient.approveLyrics` call **before** render starts (409 otherwise) — it is a separate committed step, not implicit.
- Gift-context content handoff (`completeGiftSongIfNeeded`) fires as soon as content exists, using a `didHandOffGiftContent` once-guard to survive callback races — happens **before** the user reaches Reveal.
- `RevealBloomView`'s reaction-prompt button fires the exact same `onShare` action as the primary share button — framing-only, not a separate flow.
- `SharePostcardView`: `onSend` is **only** invoked as a fallback when no share URL/PIN exists yet — every successful tile tap bypasses it entirely; wiring all tiles through one handler double-presents sheets.
- `DirectSendModel`'s WhatsApp "Sent!" confirmation is inferred via a background→foreground NotificationCenter round-trip heuristic (no OS signal exists) — must guard against false positives from incidental foregrounding (e.g. Control Center).
- Contact picker must be presented **imperatively** on the topmost UIViewController when nested inside a `.sheet`-inside-`.fullScreenCover`, because `CNContactPickerViewController`'s self-dismissal cascades and tears down the entire parent flow if presented as a native SwiftUI `.sheet`.

**Player**

- `PlayerState` vocal-onset detection: samples average dB power for the first 1.0s as an instrumental-only baseline, flags onset after sustained (9 consecutive ~33ms frames, ~300ms) power exceeding baseline+8dB, backdates the detected time by 0.3s to compensate for detection lag, with a hard 20s safety timeout forcing onset regardless.
- Lyric lead-time/acceleration curves differ per visual style (Spotlight 0.45 coefficient, Verse Stage 0.30, Karaoke Sweep 0.25) — deliberately tuned per animation type, not a shared linear formula.
- `TrackPlayerFullView`'s lyric sync is a much simpler linear/proportional-index fallback with **no** vocal-onset gating — the two player implementations are NOT unified and must not be conflated in an Android port.
- `NowPlayingView`'s whole-screen drag-to-dismiss only responds to downward translation (upward drags ignored), damped at 0.5×, dismisses only past 100pt.
- `MySongsView` audio-load task explicitly cancels any in-flight prior load before starting a new one, with multiple `Task.checkCancellation()` checkpoints plus a final track-ID match guard to prevent stale downloads clobbering a newer selection.
- Interruption-handler registration must be explicitly idempotent (remove-then-re-add) or repeated sign-out/sign-in cycles leak observers causing duplicate pause-on-interruption firing forever.

**Billing**

- `blocksRepeatPurchase` deliberately includes the `.success` state (not just loading/purchasing) to keep buy buttons disabled during the 1-second post-purchase dismiss delay, preventing a double-charge from a stray double-tap.
- Free subscription tier is hidden once credits reach 0 (`visiblePlans` filter) — a naive port showing it produces a dead 0-credit card.
- `GiftBagView` refreshes both on `.task` (initial) **and** `.onChange(of: scenePhase)` returning to `.active` — required because StoreKit purchases (Ask to Buy, lockscreen approval) can complete entirely outside the app process.
- `currentCredits` reads only `songsRemaining` OR `poemsRemaining` based on context — never sums both; summing would show wrong credit counts.

**Share/Poem Claim**

- Device-bound authenticated audio streams require custom headers (`x-device-id`, `x-platform`, optional `x-device-token`) — omitting these causes 401/403.
- `reClaimPoem()` deliberately re-calls the claim endpoint with an empty PIN string even when no PIN was ever required, because the backend endpoint is idempotent and this is the only way to fetch full poem content post-claim.
- Poem-share and song-share error-message mapping are two **separately implemented, slightly divergent** string-matching functions (`mapPoemShareError` vs `mapShareError`) — verify against actual backend codes before consolidating (song and poem backends may genuinely differ).
- Social share URLs are cache-busted before every share tap by stripping prior `fbv`/`smv`/`sp` query params and re-stamping fresh ones — otherwise social platforms serve a stale cached link preview.

**Voice/Audio Capture**

- `AVAudioSession` is deliberately set to `.measurement` mode (not `.voiceChat`) for recording — voice-chat mode's echo cancellation/AGC/noise-reduction would destroy singing/voice-enrollment audio quality. Android equivalent must explicitly avoid `AcousticEchoCanceler`/AGC/NS or use `VOICE_RECOGNITION`/`UNPROCESSED` audio source, not `VOICE_COMMUNICATION`.
- Recording output is always downmixed to mono 16-bit regardless of source channel count; a 0.5s/22,050-sample floor rejects too-short recordings client-side before upload.
- `LaunchFlashView` deliberately uses `.playback` audio category so its auto-playing snippet plays even with the hardware silent switch engaged.

**App Lifecycle**

- ATT (App Tracking Transparency) authorization request is deliberately deferred until `scenePhase == .active` (not `applicationDidFinishLaunching`) — Apple silently returns current status without prompting if requested too early, e.g. during splash animation.
- Two independent push-notification systems coexist by design: native APNs for transactional/render-complete pushes, OneSignal for marketing — Android's FCM + OneSignal equivalent must mirror this split carefully to avoid duplicate or missing notifications.

## 5. Coverage Gaps
